# ADR-0001：W16 MVP 范围冻结

- 状态：Accepted（2026-10-29 确认）
- 日期：2026-10-29
- 截止：W16 Release Gate，2027-02-21
- 复核点：SC-0101、W8（下单核心）、W10（售后闭环）、W12（测试/迁移）、W16
- 关联：`docs/adr/0000-technology-baseline.md`、`docs/plan/SmartCommerce_AI_v2_Development_Manual_238_Days.md` 0.3 与第 7 章

## 背景

238 天计划里真正的投递窗口从 2027-02（W17）开始。W16 必须交付一个可演示、可部署、能讲清楚的交易后端 MVP；AI 能力是第二里程碑，不能阻塞投递。没有范围冻结，Should/Could 会挤占 Must 和测试时间。

## 决策

### 1. W16 必须有（Must 功能）

| 领域 | 最小范围 |
|---|---|
| 认证 | 注册、登录、BCrypt/Argon2、令牌校验、用户数据隔离 |
| 权限 | USER/ADMIN/SUPPORT 角色、资源所有权、管理端保护 |
| 商品 | 列表/详情、管理端创建/修改/上下架、参数校验、分页与稳定排序 |
| 购物车 | 加购、改数量、删除、本人数据隔离 |
| 订单 | 服务端价格快照、创建订单、明确状态机、取消 |
| 库存 | 条件扣减、防超卖、库存流水 |
| 幂等 | Idempotency-Key；同键不同请求体返回冲突 |
| 支付模拟 | 回调处理；重复、乱序、伪造回调不重复变更状态 |
| 取消补偿 | 未支付取消回补库存；重复取消不重复回补；支付/取消竞争只产生一个合法终态 |
| 售后 | 售后工单提交/查询/客服审核（模拟）；USER 不能自行标记已处理 |
| 事件链路 | Outbox + 至少一个幂等消费者；断网恢复可补发 |
| 工程 | Flyway、统一错误契约 + requestId、单元/集成测试、OpenAPI、结构化日志 |

### 2. W16 发布交付物

- `infra/compose.yaml`：健康检查、启动顺序容错。
- `Dockerfile`：多阶段构建、非 root、运行镜像不含密钥。
- `scripts/deploy-local.sh`：干净环境一条命令启动。
- `tests/e2e/smoke.sh`：注册→商品→购物车→下单→支付→售后，退出码准确。
- `docs/security/mvp-check.md`：CORS、敏感日志、Actuator、依赖漏洞检查。
- `docs/career/resume-project-v0.md`：只写已通过测试的成果，量化数据标注环境。
- `release/v0.1.0.md` + `docs/reviews/week16.md`：可部署版本与未通过 P0 清单。
- 3 分钟 demo 录像 + README 一键复现。

### 3. AI 第二里程碑（W19 之后，不作为 W16 前置）

- RAG 售后 FAQ：引用来源、无依据拒答/转人工、撤回政策失效。
- 只读订单工具：`getMyOrderStatus(orderId)`，userId 来自 SecurityContext。
- AI 工单草稿：客服审核后才成为正式回复。
- 评测：约 40 条黄金集、FakeProvider、超时/降级/成本预算。

### 4. 可以砍/延期

- 完整运营后台 UI、MCP（W27）、复杂 Agent、多模型同时接入。
- 完整 Prometheus/Grafana/OTel 栈；Actuator/Micrometer 放 W18，W16 只保留 requestId + 结构化日志。
- 性能压测优化、灰度策略、额外前端。
- 不影响 Must 验收的重构和“更优雅”的抽象。

### 5. 明确不做

- 真实收款/物流/退款、真实用户数据导入。
- 微服务拆分、千万 QPS、模型训练。
- LLM 直接修改订单、退款或绕过认证。

## 硬规则

1. W16 前，任何 Should/Could 任务只要影响 Must 或测试，直接延期。
2. Must 用例失败不得宣布 MVP 完成；先修复，再投递。
3. 每张 Must 工单必须有 evidence（测试/命令/文档）；没有证据视为未完成。
4. 不伪造压测、RAG、成本数据；没有测量就写“未测量”。
5. 范围变更必须更新本 ADR，并在 `STATUS.md` 和 daily 记录原因。

## W16 验收脚本

1. 干净环境 `docker compose ... up -d`，`./mvnw test` 全绿。
2. 注册 → 登录 → 管理员建商品并上架。
3. 用户加购 → 下单（带 Idempotency-Key）→ 库存扣减。
4. 重复提交同一键不重复建单；同键不同体返回冲突。
5. 模拟支付回调；重复/乱序/伪造回调不重复变更状态。
6. 取消未支付订单 → 库存回补；重复取消不重复回补。
7. 并发抢最后一件商品：最多一单成功，库存不为负。
8. 用户 A 无法查询/操作 B 的订单。
9. 售后工单：USER 提交/查询，SUPPORT 审核；USER 不能自行完结。
10. 支付成功事件最终投递，重复消费只产生一次通知。
11. 陌生机器按 README 部署并跑通 smoke 脚本。

## 后果

- 正面：W16 有可投递的交易 MVP；面试能讲清库存、幂等、状态机、Outbox、售后。
- 负面：后台 UI、完整观测栈、MCP、AI 功能延后；需要主动砍功能。
- 落后时：先砍 Should/Could 和界面，不砍测试、鉴权、幂等、库存正确性。

## 复核

- Must 清单和砍单清单已于 2026-10-29 确认。
- W8/W10/W12 各复核一次；W16 Gate 前不再扩大范围。
